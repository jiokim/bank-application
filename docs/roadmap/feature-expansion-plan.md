# 기능 확장 계획

이 문서는 현재 대출 멀티상품 조회 프로젝트에서 추가로 확장할 수 있는 기능을 정리한다. 기능 후보는 대규모 시스템 설계 관점에서 자주 다루는 캐시, 멱등성, 이력 관리, 조회 확장, 이벤트 분리를 금융 도메인에 맞게 적용하는 방향으로 선정했다.

## 확장 방향

현재 구조는 상품, 계약, 대출, 예금 도메인을 분리하고 대출 멀티상품 조회를 처리할 수 있도록 구성되어 있다. 이후 기능 확장은 다음 기준을 우선한다.

- 24시간 비대면 대출 신청 환경에서 중복 요청과 재시도에 안전한 구조
- 상품 정보처럼 반복 조회되는 데이터에 대한 조회 효율 개선
- 계약 상태 변경과 거래 이력의 추적 가능성 확보
- 대출, 예금 등 상품군이 늘어나도 고객 기준 통합 조회가 가능한 구조
- 기능 추가 시 특정 도메인 구현체에 강하게 결합되지 않는 의존 방향 유지

## 1. 대출 신청 멱등성 보장

### 문제 상황

비대면 대출 신청에서는 고객의 반복 클릭, 네트워크 재시도, 외부 채널의 재전송으로 동일 요청이 여러 번 들어올 수 있다. 이때 동일 신청이 중복 생성되면 심사, 한도, 실행 단계까지 중복 처리될 수 있다.

### 기능 목표

같은 대출 신청 요청이 반복으로 들어와도 신청 건은 한 번만 생성되도록 보장한다. 이미 처리된 요청은 기존 처리 결과를 반환하고, 같은 멱등 키로 다른 요청이 들어오면 충돌로 처리한다.

### 설계 방향

- 대출 신청 API에서 `Idempotency-Key`를 수신
- `Idempotency-Key`, 고객 ID, 요청 해시를 함께 저장
- 동일 키와 동일 요청 해시가 다시 들어오면 기존 신청 결과 반환
- 동일 키지만 요청 내용이 다르면 `409 Conflict` 처리
- 멱등성 저장소는 대출 신청 흐름과 분리해 재사용 가능한 구조로 설계

### 기대 효과

- 고객 반복 클릭으로 인한 중복 대출 신청 방지
- 외부 채널 재전송 상황에서도 동일 요청의 중복 처리 방지
- 심사, 실행 등 후속 업무 단계의 중복 호출 가능성 감소

### 우선순위

가장 먼저 적용할 기능으로 본다. 현재 대출 신청과 직접 연결되고, 금융 도메인에서 안정성을 설명하기 좋은 기능이다.

## 2. 상품 기준 정보 로컬화 및 캐시

### 문제 상황

상품 서버가 별도로 존재하고, 대출 업무에서는 상품 서버에서 관리하는 상품 기준 정보를 참조해야 한다. 대출 멀티상품 조회나 대출 신청 과정에서 매번 상품 서버를 직접 호출하면 상품 서버 장애나 네트워크 지연이 대출 업무에 직접 영향을 줄 수 있다.

실제 운영 구조에서는 상품 기준 정보를 배포 방식으로 대출 DB에 반영하고, 대출 업무는 로컬 DB에 적재된 상품 기준 정보를 조회하는 방식이 적합하다.

### 기능 목표

상품 서버의 기준 정보를 대출 업무에서 안정적으로 참조할 수 있도록 로컬 상품 기준 테이블 또는 읽기 모델을 구성한다. 반복 조회되는 상품 기본 정보는 로컬 DB 기준으로 조회하고, 필요 시 애플리케이션 캐시를 추가로 적용한다.

### 설계 방향

- 상품 서버는 상품 기준 정보의 원천 시스템 역할을 담당
- 대출 서버는 배포된 상품 기준 정보를 로컬 DB에 저장해 조회
- `loan-core`는 상품 저장 방식이나 배포 방식을 직접 알지 않고 상품 조회 계약에 의존
- 상품 기준 정보에는 배포 버전, 적용 시작일, 적용 종료일, 판매 상태를 함께 관리
- 상품 변경 시 배포 이력과 적용 시점을 기준으로 대출 업무에 반영
- 로컬 DB 조회가 반복되는 경우 상품 ID 기준 애플리케이션 캐시를 추가 적용

### 로컬화 대상

- 상품 ID
- 상품명
- 상품 유형
- 상품 분류 코드
- 판매 상태
- 적용 시작일
- 적용 종료일
- 상품 조건 요약

### 캐시 제외 또는 주의 대상

- 고객별 대출 한도
- 심사 결과
- 계약 상태
- 실행 가능 여부
- 실시간 금리 계산 결과

### 기대 효과

- 상품 서버 장애나 지연이 대출 조회와 신청 업무에 직접 전파되는 위험 감소
- 대출 업무에서 필요한 상품 기준을 로컬 DB 기준으로 안정적으로 조회
- 상품 변경 시 배포 버전과 적용 시점을 기준으로 업무 반영 범위 추적 가능
- 멀티상품 대출조회 시 반복 상품 조회 비용 감소
- 상품 기준 정보와 고객별 계약/심사 정보의 책임 분리

### 구현 시 고려사항

- 상품 기준 정보 배포가 실패했을 때 기존 버전으로 계속 조회할지, 특정 상품 신청을 제한할지 정책 필요
- 상품 판매 중지나 조건 변경처럼 업무 영향이 큰 변경은 적용 시점을 명확히 관리
- 대출 신청 시점에 어떤 상품 버전을 기준으로 신청했는지 기록 필요
- 로컬 DB에 배포된 상품 정보와 상품 서버 원천 데이터 간 정합성 점검 배치 고려

## 3. 계약 상태 변경 이력

### 문제 상황

대출 신청, 심사, 계약 생성, 실행 등 계약 상태가 변경되는 과정에서 상태 변경 사유와 시점이 남지 않으면 운영 중 오류 원인 파악이 어렵다.

### 기능 목표

계약 상태가 변경될 때마다 이전 상태, 변경 상태, 변경 사유, 변경 시각을 기록한다.

### 설계 방향

- 공통 계약 모델 기준으로 상태 변경 이력 모델 추가
- 상태 변경 시 이력 저장을 업무 처리 흐름에 포함
- 계약 상세 조회 시 상태 변경 이력을 함께 조회할 수 있도록 확장

### 기대 효과

- 운영 중 상태 변경 추적 가능
- 오류 발생 시 어느 단계에서 문제가 생겼는지 확인 가능
- 감사나 업무 문의 대응에 필요한 근거 데이터 확보

## 4. 고객 기준 통합 계약 조회

### 문제 상황

대출, 예금 등 상품군이 늘어나면 고객이 보유한 계약을 상품별 API로 각각 조회해야 한다. 이 경우 고객 기준의 통합 화면이나 통합 조회 기능을 만들기 어렵다.

### 기능 목표

고객 ID 기준으로 대출, 예금 등 여러 상품군의 계약 요약 정보를 한 번에 조회할 수 있는 API를 제공한다.

### 설계 방향

- `arrangement-core`의 공통 계약 모델을 기준으로 계약 요약 응답 구성
- 상품별 상세 정보는 각 도메인 모듈에서 조회
- 서비스 계층에서 상품군별 계약 요약을 집계
- 응답에는 계약 유형, 상품명, 계약 상태, 계약 기간 등 공통 정보 중심으로 제공

### 기대 효과

- 고객 기준 통합 계약 조회 가능
- 상품군이 늘어나도 공통 계약 응답 구조 재사용
- 대출, 예금 등 개별 도메인의 상세 규칙은 각 모듈에 유지

## 5. 조회 API 페이징, 정렬, 필터링

### 문제 상황

계약 데이터가 늘어나면 전체 목록을 한 번에 조회하는 방식은 응답 시간이 길어지고 화면 처리도 어려워진다.

### 기능 목표

고객별 계약 목록이나 대출 조회 결과에 페이징, 정렬, 필터링을 적용한다.

### 설계 방향

- 계약 상태, 상품 유형, 신청일자 기준 필터 제공
- 최신순, 상태순 등 정렬 기준 제공
- offset 기반보다 cursor 기반 페이지네이션을 우선 검토

### 기대 효과

- 대량 계약 데이터 조회 시 응답 안정성 개선
- 화면에서 필요한 범위만 조회 가능
- 계약 데이터 증가에 대응 가능한 조회 구조 확보

## 6. 계약 상태 변경 이벤트 처리

### 문제 상황

계약 상태 변경 이후 이력 저장, 알림, 거래 생성 등 후속 처리를 직접 호출 방식으로 묶으면 상태 변경 로직이 복잡해진다.

### 기능 목표

계약 상태 변경 이후 필요한 후속 처리를 이벤트로 분리한다.

### 설계 방향

- 계약 상태 변경 시 도메인 이벤트 발행
- 상태 변경 이력 저장, 알림, 거래 이력 생성 등은 이벤트 구독자에서 처리
- 초기 구현은 Spring `ApplicationEvent` 또는 in-memory publisher로 시작
- 이후 필요하면 메시지 큐 기반 구조로 확장 가능

### 기대 효과

- 상태 변경 로직과 후속 처리 책임 분리
- 새로운 후속 기능 추가 시 기존 상태 변경 로직 수정 최소화
- 이벤트 기반 처리 구조로 확장 가능

## 공통 프레임워크 / 자동화

### 7. 대외계 자동 복호화 (SensitiveDecryptingModule)

#### 문제 상황

`@Sensitive` 필드는 시스템 내부에서 암호화 상태로 유지된다. 대외계(NICE, KCB, SGI, KIFA 등)로 전문을 전송할 때는 복호화된 값이 필요하지만, 개발자가 매번 명시적으로 `processForRestore()`를 호출해야 하는 부담이 있다. 호출 누락 시 암호화된 값이 그대로 전송된다.

#### 설계 방향

- 대외계 전용 `RestClient` Bean을 별도로 등록한다.
- 이 Bean에 `@Sensitive` 필드를 직렬화 시점에 자동 복호화하는 `SensitiveDecryptingModule` (Jackson `SimpleModule`)을 탑재한다.
- 외부 클라이언트는 이 Bean만 주입받으면 복호화 처리가 자동으로 된다.
- 객체를 mutate하지 않고 직렬화 시점에만 복호화하므로 내부 상태가 오염되지 않는다.

```
내부: @Sensitive 필드 암호화 상태 유지
외부 전송: externalRestClient → SensitiveDecryptingModule → 복호화된 값으로 직렬화 → 대외계
```

BXM의 `ExtrnlLinkMgmt` + XP 레이어가 이 경계 역할을 프레임워크 수준에서 담당했던 것과 같은 원칙이다.

### 8. ArchUnit 아키텍처 규칙 자동 검증

#### 문제 상황

`-api / -core / -svc` 레이어 규칙과 도메인 간 의존 방향은 현재 개발자가 기억해서 지킨다. 규칙 위반이 발생해도 빌드에서 잡히지 않는다.

#### 설계 방향

ArchUnit으로 다음 규칙을 테스트로 고정한다.

- `-api` 모듈은 Spring 의존 금지
- `-svc`는 다른 도메인의 `-svc`를 참조 금지
- `@Sensitive`가 붙어야 할 Value Object 타입(`AccountNo`, `Rrn` 등)에 어노테이션 누락 시 빌드 실패

los-apps 이식 시 의존성 오염을 자동으로 감지하는 데도 활용한다.

### 9. Value Object 기반 민감정보 타입

#### 문제 상황

계좌번호, 주민등록번호 등 민감정보를 `String`으로 다루면 `@Sensitive` 누락을 탐지하기 위해 필드명 패턴 하드코딩에 의존해야 한다. 필드명이 달라지면 탐지가 불가능하다.

#### 설계 방향

민감정보를 Value Object로 감싼다.

```java
public record AccountNo(String value) {
    public AccountNo {
        if (!value.matches("\\d{10,14}")) throw new IllegalArgumentException("잘못된 계좌번호");
    }
}
```

- 타입 자체가 민감정보임을 표현한다.
- ArchUnit에서 타입 기반으로 `@Sensitive` 누락을 탐지할 수 있다.
- 생성자에서 형식 검증이 보장된다.
- 민감정보 + 유효성 검증 + ArchUnit 탐지를 타입 하나가 동시에 처리한다.

### 10. BXM 패턴 자동 탐지 및 변환 (OpenRewrite)

#### 문제 상황

los-apps 이식 시 `CbbApplicationContext.getBean()`, `@BxmService`, BXM 전용 어노테이션을 수작업으로 하나씩 찾아 변환해야 한다.

#### 설계 방향

- `grep` 스크립트로 BXM 의존 패턴 위치와 규모를 먼저 파악한다.
- 반복 변환 패턴은 OpenRewrite 레시피로 자동화한다.
  - `CbbApplicationContext.getBean(X.class, x)` → `@Autowired` 생성자 주입으로 변환
  - `@BxmService` → `@Service` 변환
- 자동 변환 후 ArchUnit으로 남은 BXM 의존성이 없는지 검증한다.

## 추천 적용 순서

1. 대출 신청 멱등성 보장
2. 상품 기준 정보 로컬화 및 캐시
3. 계약 상태 변경 이력
4. 고객 기준 통합 계약 조회
5. 조회 API 페이징, 정렬, 필터링
6. 계약 상태 변경 이벤트 처리

## 이력서 어필 포인트

- 비대면 대출 신청에서 반복 요청과 재시도를 고려해 멱등성 보장 구조 설계
- 상품 서버의 기준 정보를 대출 DB에 배포하고 로컬 조회 구조로 구성해 대출 업무의 조회 안정성 확보
- 계약 상태 변경 이력을 분리해 운영 중 오류 추적과 감사 대응이 가능한 구조로 개선
- 대출, 예금 계약을 공통 계약 모델로 추상화하고 고객 기준 통합 조회가 가능한 구조로 확장
- 공통 모델과 상품별 규칙을 분리해 신규 상품 추가와 규정 변경 시 영향 범위를 줄이는 방향으로 설계

# ADR 000: docs 디렉터리 구조 설계

## 상황

이 프로젝트의 docs는 단일 목적이 아니다. 세 가지 목표가 동시에 존재한다.

| 목표 | 독자 |
|---|---|
| 면접 포트폴리오 | 면접관 |
| 팀 온보딩 | 미래 협업자, 코드를 처음 보는 사람 |
| 기술 성장 + 설명 연습 | 본인 |

독자가 다르면 필요한 문서가 다르다.

## 결정

```
docs/
├── architecture/          ← 면접관용: 왜 이렇게 설계했나
│   ├── domain-model.md
│   ├── common-framework.md
│   └── adr/               ← 설계 결정 근거
├── features/              ← 온보딩용: 이 기능이 뭔지, 어떻게 쓰는지
├── guides/                ← 학습·설명 연습용: 왜 이 기술이 이렇게 동작하는지
├── build/                 ← Gradle 구성
└── roadmap.md
```

## 각 디렉터리 역할

**features/** — 온보딩하는 사람이 읽는다.
- 기능 목적, 요청/응답 예시, 적용 방법 중심
- "이 기능을 내일부터 쓰려면 무엇을 알아야 하는가"

**guides/** — 본인이 읽고, 설명 연습을 위해 쓴다.
- 왜 이 설계인가, Spring 내부는 어떻게 동작하는가 중심
- 같은 기능이라도 features/와 관점이 다르다
- guides/ 작성 원칙은 `guides/README.md` 참고

**architecture/** — 면접관과 의사결정자가 읽는다.
- 시스템 전체 설계 의도, 모듈 경계, 도메인 모델
- adr/ 하위에 설계 결정 하나당 파일 하나

## 이유

초기 구조(Codex 생성)에서 features/와 guides/가 같은 주제를 두 번 다뤘다.
원인은 독자를 정의하지 않고 파일을 나눴기 때문이다.

독자를 먼저 정의하면 디렉터리 역할이 자연스럽게 분리된다.
같은 기능이 두 디렉터리에 있어도 관점이 다르면 중복이 아니다.

## ADR을 도입한 이유

설계 결정은 코드에 남지 않는다. 왜 HandlerInterceptor가 아닌 RequestBodyAdvice인지,
왜 AES-GCM인지는 코드만 봐서는 알 수 없다.

ADR은 이 "왜"를 파일 하나로 기록한다. 팀에 설명할 때, 면접에서 답변할 때
구두 설명 없이 파일 하나를 보여주면 된다.

# ADR 001: 회사 도입 전략

## 상황

이 설계를 기존 회사 레거시 시스템에 도입하려면 세 가지 장벽이 있다.

1. **"지금 잘 돌아가는데 왜 바꿔요"** — 현재 방식의 문제를 구체적으로 보여줘야 한다
2. **"한꺼번에 바꿀 수 없어요"** — 점진적 도입 경로가 없으면 채택이 안 된다
3. **"우리 팀이 이해 못해요"** — 팀 전체가 이해해야 유지보수가 된다

## 점진적 도입 순서

```
1단계: bank-common만 도입
       @Sensitive, StoragePolicy 어노테이션
       Spring 비의존 → 기존 코드 침투 최소화
       누구든 어노테이션 하나 추가하는 것부터 시작 가능

2단계: bank-common-core 도입
       PreServiceSensitiveFieldHandler, AutoConfiguration
       신규 API부터 적용 → 기존 API는 그대로 유지

3단계: BankRequestContext + TransactionJournalAspect
       의존성 추가만으로 자동 적용
       기존 서비스 코드 수정 없음
```

AutoConfiguration + ConditionalOnMissingBean 구조가 이 점진적 도입을 가능하게 한다.
팀이 원하면 특정 빈만 오버라이드해서 커스터마이징할 수 있다.

## 설득 방법

기술이 좋아도 설득에 실패하면 도입이 안 된다.

- "우리 설계가 더 낫다"가 아니라 "현재 방식에서 이 문제가 반복되고, 이 설계는 그걸 이렇게 해결한다"
- 레거시를 나쁘다고 하지 않는다. 당시 상황에서 최선의 선택이었을 수 있다
- ADR로 "왜 이 결정인가"를 미리 문서화해두면 팀 리뷰에서 구두 설명이 줄어든다

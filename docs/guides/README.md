# guides/ 작성 가이드

guides/는 **왜 이 기술이 이렇게 동작하는가**를 설명하는 공간이다.

- features/: 온보딩용. "이 기능이 뭔지, 어떻게 쓰는지" (What + How-to-use)
- guides/: 학습·설명 연습용. "왜 이 설계인가, Spring 내부는 어떻게 동작하는가" (Why + Deep-dive)

같은 기능이라도 두 문서의 관점이 다르다. 겹치는 내용이 생기면 guides/에서 features/로 링크만 남긴다.

---

## guides/를 쓰는 이유

설명할 수 있는 사람만이 진짜 이해한 사람이다.

guides/를 쓰는 행위 자체가 학습이다. 문장을 쓰다 막히는 지점이 곧 이해가 부족한 부분이다. "첫 줄을 못 쓰겠다"면 문제 정의가 아직 안 된 것이다.

---

## 좋은 기술 설명의 구조

기술 설명은 항상 이 순서로 쓴다.

```
1. 문제가 뭐였나      ← 맥락. 이게 없으면 독자가 왜 읽어야 하는지 모름
2. 해결책 한 문장     ← 전체 그림을 먼저 줌. 세부 설명은 그 다음
3. 어떻게 동작하나    ← 메커니즘 설명
4. 왜 다른 방법 아닌가 ← 판단력을 보여주는 부분. 면접에서 가장 많이 나옴
```

예시:

```
❌ "RequestBodyAdvice는 afterBodyRead 메서드를 오버라이드해서 DTO를 받은 뒤에 처리합니다."
   → 어떻게 동작하는지만 설명. 왜인지 없음.

✅ "컨트롤러마다 encrypt()를 직접 호출하면 암호화 누락이 생긴다. (문제)
   RequestBodyAdvice로 DTO 역직렬화 직후에 공통 처리를 끼워넣었다. (해결책)
   afterBodyRead는 JSON → DTO 변환 직후, 컨트롤러 호출 전에 실행된다. (동작)
   HandlerInterceptor는 이 시점에 DTO 필드에 접근할 수 없어서 선택하지 않았다. (판단)"
```

## 작성 시 체크리스트

- [ ] 첫 섹션이 "문제 상황"으로 시작하는가
- [ ] 해결책을 한 문장으로 쓸 수 있는가
- [ ] "왜 A가 아니라 B인가"에 답했는가
- [ ] 코드 스니펫보다 설명이 먼저 나오는가
